# План моста Яндекс Алиса ↔ ChatGPT/Codex

## 1. Цель и границы

Цель — дать пользователю навыка Яндекс Алисы голосовой доступ к локально
авторизованному Codex. Рабочий PoC
[`poc/app-server/codex_app_server.py`](poc/app-server/codex_app_server.py)
служит только источником проверенного кода и протокольных решений: его не
запускают и не поставляют как часть итоговой системы.
Название «ChatGPT» далее означает ответ Codex в аккаунте, в котором выполнен
`codex login`; это **не** OpenAI Platform API и не browser automation.

Первый результат — личный MVP: один владелец, один локальный компьютер,
текстовый ответ Алисы в пределах синхронного webhook-запроса. В границы MVP не
входят публичный multi-tenant сервис, произвольные серверные уведомления в
диалог Алисы, платежи, общий доступ к Codex-аккаунту и автоматическое
одобрение tool-вызовов.

## Текущий статус MVP

Выполнено:

* [x] Loopback webhook с проверкой JSON-запроса Яндекс Диалогов и корректным JSON-ответом.
* [x] Непубличный webhook path, лимиты тела запроса, health endpoint и безопасные lifecycle-логи.
* [x] Самостоятельный JSONL-адаптер для `codex app-server`: handshake, `thread/start`, `turn/start`, ожидание `turn/completed` и timeout.
* [x] Одна общая сессия Codex с истечением через час без сообщений и командами «новый разговор»/«удали историю».
* [x] Короткое подтверждение через 3 секунды и выдача завершённого фонового ответа на «Ну что?» и похожие фразы.
* [x] Настройки `ALICEGPT_EPHEMERAL` (по умолчанию `false`) и изолированного непроектного `ALICEGPT_CWD=/private/tmp`.
* [x] Ручная проверка HTTPS tunnel, webhook и валидного ответа через публичный URL.

Остаётся:

* [ ] Голосовая проверка опубликованного приватного навыка на колонке и стабильный tunnel URL.
* [ ] Восстановление persistent thread после перезапуска daemon — намеренно не реализуется в текущем MVP.
* [ ] Dedupe повторных доставок, rate limit, метрики и production-grade аутентификация webhook.

## 2. Целевая архитектура и поток

```text
Пользователь → Алиса / Яндекс Диалоги → HTTPS webhook
                                      → alicegpt-agent (local daemon)
                                      → Codex app-server --stdio (JSONL)
                                      → авторизованный локальный Codex
                                      → webhook JSON → Алиса → пользователь
```

`alicegpt-agent` — долгоживущий локальный HTTP-сервис и единственная новая
интеграционная точка. Он принимает webhook, проверяет его, определяет сессию,
передаёт текст в собственный `codex_adapter` и возвращает допустимый JSON
Яндекс Диалогов. `codex_adapter` создаётся копированием и адаптацией нужных
частей PoC, затем живёт и тестируется независимо от него. Адаптер владеет
дочерним `codex app-server`, выполняет handshake
`initialize → initialized`, создаёт/возобновляет thread, посылает `turn/start`
и ждёт `turn/completed`.

Нормальный запрос: (1) Яндекс вызывает webhook; (2) агент валидирует JSON и
дедуплицирует доставку; (3) роутер выбирает Codex thread; (4) агент запускает
turn с ограничением времени; (5) извлекает финальный `agentMessage`; (6)
обрезает/нормализует ответ под Алису и отдаёт его в том же HTTP-ответе.

## 3. Рекомендованный MVP: без центрального gateway

На компьютере владельца постоянно работает `alicegpt-agent`, а внешний HTTPS
адрес предоставляет public tunnel (например, Cloudflare Tunnel, ngrok или
аналог). В настройках навыка Яндекс Диалогов указывается URL tunnel вида
`https://<random-subdomain>.<provider-domain>/alice/webhook`.

### Плюсы

* Минимум инфраструктуры, стоимости и секретов: Codex OAuth-сессия никогда не
  покидает компьютер.
* Быстрее проверить голосовой UX и реальное время ответа Codex.
* Нет собственного публичного сервера, базы данных или межсервисного канала.

### Минусы и эксплуатационные ограничения

* Компьютер, локальный daemon и tunnel должны быть включены; сон, перезагрузка
  и смена сети делают навык временно недоступным.
* Бесплатный tunnel может менять URL или иметь лимиты. Для стабильного навыка
  нужен зарезервированный hostname и health-check/автозапуск.
* Tunnel публикует endpoint в интернете. Сам агент должен слушать только
  `127.0.0.1`; наружу его выпускает исключительно tunnel. Нельзя открывать
  порт daemon напрямую на роутере.
* TLS должен завершаться у проверенного tunnel-провайдера с валидным публичным
  сертификатом. HTTP, self-signed TLS, IP-адрес вместо hostname и редиректы не
  считать поддерживаемой конфигурацией.

Минимальная защита endpoint: длинный случайный непубличный path, проверка
подписи/секрета webhook по актуальной документации Яндекса (если доступна для
выбранного типа навыка), allow-list формата запроса, rate limit и ограничение
тела запроса. Path не заменяет аутентификацию. Секреты хранятся в keychain или
файле с правами владельца, не в репозитории и не в логах.

## 4. Когда нужен gateway

Вариант с gateway добавляет публичный HTTPS-сервис:

```text
Алиса → gateway (auth, rate limit, очередь, session registry) ⇄ защищённый
outbound-канал ⇄ alicegpt-agent на одном или нескольких компьютерах → Codex
```

Gateway становится оправданным, когда нужен хотя бы один из пунктов: постоянный
домен и наблюдаемая доступность независимо от домашней сети; несколько агентов
или пользователей; центральные политика доступа, аудит, лимиты и billing;
очередь/маршрутизация; защищённое хранение метаданных сессий; rollout без
ручной перенастройки навыка. Он увеличивает стоимость, поверхность атак и
ответственность за персональные данные, а также требует mTLS или
короткоживущих токенов для агентского outbound-канала.

**Рекомендация:** начать с local daemon + managed HTTPS tunnel. Вводить gateway
только после подтверждения UX, измерения latency/доступности и появления
реального требования multi-user или постоянного публичного SLA.

## 5. Контракт `alicegpt-agent`

### Webhook и валидация

* `POST /alice/webhook`, `Content-Type: application/json`; ограничить размер
  body и время чтения.
* Разобрать JSON строго по актуальной схеме Яндекс Диалогов: обязательные
  `meta`, `session` и `request`; не полагаться на необязательные поля.
* Проверить версию протокола, тип request, подпись/источник, если платформа их
  предоставляет, и безопасно отклонить неизвестные форматы (`4xx`, без деталей
  внутренней реализации).
* Использовать `session.session_id` как ключ идемпотентности доставки, а
  `session.message_id` (либо эквивалентный актуальный идентификатор сообщения)
  — как ключ конкретной реплики. Хранить короткий TTL-кэш последних ответов:
  повтор запроса должен вернуть уже сформированный JSON, а не создать второй
  turn.
* Идентификатор пользователя брать из `session.user.user_id`, а идентификатор
  приложения/навыка — из `session.application.application_id`; оба пути перед
  реализацией обязательно сверить с актуальной схемой Яндекс Диалогов и
  реальным fixture. Хранить пользовательский идентификатор только как salted
  hash. Не логировать сырые user/session IDs, голосовой текст или OAuth-данные
  без явного debug-opt-in.

### Вызов Codex и отмена

В новый `codex_adapter` копируются и адаптируются проверенные части PoC: запуск
`codex app-server --stdio`, потокобезопасное чтение JSONL, handshake,
`thread/start`, `turn/start`, сбор `item/agentMessage/delta`, извлечение
финального сообщения при `turn/completed`, выбор модели/effort и
lifecycle-логи. Не копировать CLI-цикл stdin: новый модуль предоставляет API
`start_or_resume_thread`, `run_turn`, `cancel_turn`, `close`. Итоговый agent не
импортирует, не исполняет и не зависит от каталога `poc/` во время работы.

На каждую Codex-thread допускать только один активный turn (async lock/очередь),
чтобы параллельные webhook-и не перемешали контекст. Установить два дедлайна:
внутренний Codex deadline и более короткий безопасный webhook deadline с
запасом на формирование ответа. При отключении клиента, истечении deadline или
закрытии daemon послать поддерживаемую текущей схемой app-server отмену
(`turn/interrupt`/эквивалент, сверенный с локально сгенерированной schema),
затем не использовать частичный текст как завершённый ответ. Если отмена не
поддержана или не подтверждена за короткий grace period, изолированно завершить
и перезапустить дочерний app-server, отметив thread как требующий resume/new.

### Ответ Алисы, timeout и pending

Webhook должен вернуть ответ в лимит времени Яндекса; конкретный лимит и поля
ответа сверять с актуальной документацией до реализации. Нельзя после
завершения webhook самовольно «допушить» вторую реплику Алисе: отдельного
произвольного server push для этого потока нет.

Если Codex не завершился вовремя, вернуть короткое безопасное сообщение
(например, «Мне нужно больше времени. Спросите меня ещё раз — продолжу.»),
сохранить состояние `pending` и продолжающийся/завершившийся результат по
message id. На **следующей фразе пользователя**: если pending готов, сначала
отдать готовый ответ или краткое продолжение; если ещё выполняется — сообщить
статус и не запускать конкурирующий turn. Команды «новый разговор», «отмена» и
явная новая тема должны очистить pending или запросить отмену.

### Правило быстрого подтверждения и выдачи готового результата

Для голосового UX agent не ждёт первый ответ Codex дольше **3 секунд**. Если
turn не завершился к этому моменту, webhook сразу возвращает короткое
подтверждение, например: «Задача принята. Спроси меня через несколько секунд.»
Turn продолжает выполняться в фоне, а его финальный ответ сохраняется как
`pending` для текущей разговорной сессии. Это не является вторым server push:
Алиса получает результат только в ответ на следующую реплику пользователя.

Фразы проверки готовности — «Ну что?», «Что там?», «Готово?», «Есть ответ?» и
эквивалентные им нормализованные варианты — не создают новый turn. Если
`pending` уже завершён, agent возвращает сохранённый финальный ответ и очищает
`pending`; если он ещё выполняется, agent повторяет краткий статус. Новая тема,
«новый разговор» и «отмена» отменяют или очищают pending по правилам выше.

## 6. Модель пользователей и разговоров

Для личного MVP использовать один локальный профиль владельца. Ключ маршрута:
`hash(session.user.user_id) + session.application.application_id`, с fallback
на `hash(session.session_id)` при отсутствии стабильного user id. Пути полей
сверить с актуальной схемой до M1. Хранить минимальную локальную запись: `route_key`,
`codex_thread_id`, `thread_mode`, timestamps, pending turn и schema version.

* **Конфигурируемый ephemeral:** по умолчанию `ALICEGPT_EPHEMERAL=false`, но
  локальная привязка thread намеренно очищается при рестарте daemon. Внутри
  работающего daemon контекст живёт до TTL; `thread/resume` после рестарта не
  выполняется.
* **Persistent resume:** остаётся отдельным opt-in развитием: хранить только
  opaque thread id локально и после рестарта делать `thread/resume` по схеме
  установленного CLI. Это потребует понятного TTL, команды удаления истории и
  предупреждения о локальном сохранении.
* **Новый разговор:** явная интент-команда Алисы создаёт новый thread,
  отвязывает предыдущий route (старый persistent thread не удаляется без
  отдельной команды) и очищает pending. Не смешивать пользователей и не
  позволять пользователю передать произвольный `thread_id`.

## 7. Безопасность и данные

Codex запускается под отдельным локальным OS-пользователем с минимальным
доступом к файлам и только к нужной рабочей директории. Prompts ограничиваются
обычным разговорным режимом; агент никогда не подтверждает tool approvals,
которые PoC пока не умеет обрабатывать. В production-подобной конфигурации
отключить опасные инструменты политикой Codex или возвращать безопасную ошибку
при запросе approval.

Ввести: лимит длины текста и частоты запросов, per-user concurrency, таймауты,
redaction в structured logs, ротацию логов, секреты вне Git, dependency/update
план для Codex CLI, health endpoint только для loopback/tunnel policy и
минимальные retention/удаление session mapping. Не передавать в промпт служебные
идентификаторы, секреты, заголовки или невалидированный JSON.

## 8. Предлагаемая структура модулей

```text
alicegpt_agent/
  main.py                 # запуск, конфигурация, graceful shutdown
  http_server.py           # POST webhook, лимиты body/deadline
  yandex_dialogs.py        # schema validation, parsing, response builder
  auth.py                  # подпись/secret, hashes, redaction
  router.py                # идемпотентность, pending, intents, thread mapping
  codex_adapter.py         # самостоятельный JSONL client, скопированный и адаптированный из PoC
  thread_store.py          # SQLite/локальное хранилище, TTL и миграции
  prompts.py               # системные ограничения и нормализация ввода
  observability.py         # structured logs, metrics, correlation ids
  config.py                # env/keychain references, validation
tests/
  unit/ integration/ manual/
```

SQLite достаточен для MVP: транзакция на dedupe/pending и уникальность active
turn. За gateway перейти к сетевому хранилищу только при multi-agent
маршрутизации.

## 10. Риски и открытые вопросы

1. Лимиты времени и актуальная webhook-схема Яндекса могут меняться; перед M2
   подтвердить по официальной документации и тестовому навыку.
2. `codex app-server` versioned вместе с CLI. На старте agent сверять версию,
   генерировать/проверять schema и не делать предположений о cancellation или
   resume API.
3. Voice UX плохо переносит длинные markdown-ответы. Нужны лимиты длины,
   plain-text нормализация и продолжение только по следующей фразе.
4. Сохранение persistent контекста и голосовых запросов имеет privacy-эффект.
   Нужны политика retention, удаление и явный opt-in.
5. Неясны: точный способ проверки подлинности webhook выбранного навыка,
   допустимая concurrency на аккаунт Codex, требуемый uptime и устройство
   «нового разговора» в сценарии Алисы. Ответить до M2/M4, не скрывая эти
   допущения в коде.

## 11. Итоговая рекомендация

Для **личного MVP**: local `alicegpt-agent` + managed public HTTPS tunnel,
ephemeral threads по умолчанию, SQLite только для короткой идемпотентности и
pending, строгие timeouts, никакого auto-approval tool calls. Это быстрее всего
проверит ценность без вывода Codex OAuth за пределы устройства.

Для **public product**: не публиковать этот MVP как есть. Сначала внедрить
gateway с устойчивым доменом, аутентифицированным outbound-каналом к агентам,
tenant isolation, abuse controls, мониторингом, хранилищем сессий, privacy/
retention политиками и явной моделью того, чей Codex/OpenAI доступ используется.
